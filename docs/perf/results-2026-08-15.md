# dsh-oc performance test results (2026-08-15)

Run: `node scripts/perf.mjs --sessions N --quiet` (temporary DSH_HOME + mock LLM +
real dsh profile + fake opencode child process; N=200/1000/5000).

| Metric | 200 | 1000 | 5000 | 10000 |
|---|---|---|---|---|
| `GET /session` hot p50 | ~91ms (uncached) | ~376ms (uncached) | ~20ms | ~32ms |
| `GET /api/session` hot p50 | ~91ms (uncached) | ~313ms (uncached) | ~2ms | ~2.5ms |
| `GET /session/:id/message` cold read p95 | ~62–87ms | ~302ms | ~1420ms | ~2801ms |
| `GET /api/session/:id/message` second read of the same session p95 | — | — | ~1.4ms | ~1.7ms |
| SSE first event | ~0.1ms | ~0.1ms | ~0.16ms | ~0.21ms |
| bridge startup | — | ~1204ms | ~2805ms | ~4807ms |
| dsh RSS | ~277MB | ~302MB | ~319MB | ~360MB |

Conclusions and fixed issues:

- **SSE blocking (fixed)**: the old implementation ran `await session.list` for
  every `session/title`/`session/created` event, which stalled the SSE stream for
  hundreds of milliseconds to seconds with many sessions. It now uses a 250ms
  debounced background refresh (`router.ts` `scheduleListRefresh`), so the mux
  stream no longer waits on the list query; the regression test
  `tests/bridge-events.spec.ts` covers "status after title is not blocked by a slow
  list".
- **bridge short TTL cache (new)**: a 1s cache for `session.list` and a 500ms
  per-page cache for `session.history`, invalidated by any mutation route and by
  SSE events. With 5000 sessions, hot list requests drop from ~1.4s p50 to 2–20ms;
  a second history read of the same session takes about 1ms.
- **startup prefetch (new)**: after the bridge starts, it prefetches the session
  list in the background and warms the tail history of the 5 most recent sessions
  in parallel; `--session` resume also prefetches the target session separately.
- **in-flight merging and derived pages (new)**: in-flight RPCs for
  `session.list`/`session.history` are shared by concurrent callers, so the startup
  prefetch and the TUI's first list request no longer scan twice; with 5000
  sessions, `GET /session` cold read p95 drops from ~1941ms to ~1378ms. The full
  tail and the 100-message page derive each other's caches, so the two history
  reads when the TUI opens a session produce only one dsh scan.
- **real titles in the session list (new)**: dsh `session.list` does not return a
  title projection (measured: no row has `projections`), so the real title can only
  be read from the `session.history` tail projection. The bridge backfills it on
  list requests (synchronous full read for ≤40 sessions; at larger scales it does
  not block the list and backfills the most recent 24 in the background at low
  concurrency) and caches it in memory, so later lists answer instantly.

### 2026-08-16 retest (5000 sessions, current develop)

| Metric | Value |
|---|---|
| `GET /session` cold p95 | ~1.36s (list scan dominates; title backfill no longer blocks) |
| `GET /api/session` cold p95 | ~75ms |
| `GET /session/:id/message` cold p50 | ~1.3–1.8s (slight contention under low-concurrency background warming) |
| second read of the same session | ~2–3ms |
| dsh RSS | ~370MB (including 24 session title projection caches) |

> Background title warming runs at concurrency 2 with a cap of 24: it does not
> block the list and does not compete too much with real history reads (the earlier
> 8-concurrency/120 cap dragged the 5000-session cold list read to 10s+, now
> fixed).
>
> The load-test report adds `measurements.titleCoverage`: two snapshots,
> `initial`/`afterWarm`, quantifying the real title coverage of the list
> (5000-session example: 17/5000 after the startup prefetch, 23/5000 after 4s of
> background warming; at small scale, ≤40 sessions, the first list already has
> full coverage).
- **>500ms regression (upstream)**: with 5000 sessions, the first
  `session.list`/`session.history` takes ~1.3–1.5s; the bottleneck is the full
  session scan in the dsh storage layer. The bridge cache can only remove repeated
  reads, and the first read of a new session or a cold page still needs
  index/cwd-based storage lookup optimization on the dsh side. The dsh-oc side has
  avoided redundant waits; a further fix requires index/cwd-based storage lookup
  optimization on the dsh side.
- 1000 sessions smoke (N4 acceptance scale) all below 500ms.
- 10000 sessions: hot paths are still millisecond-level; the first cold read is
  ~2.7–3.0s and grows roughly linearly with the session count, confirming that the
  bottleneck is the dsh storage scan rather than the bridge.

### 2026-08-16 late-night retest (after adding the protocol routes, 5000 sessions)

After adding the health/active/wait/context/single-message/per-session SSE and
other endpoints, the retest gives numbers consistent with the table above:
`GET /api/session` p50 ≈ 2ms / p95 ≈ 48ms;
`GET /api/session/:id/message` p50 ≈ 1ms / p95 ≈ 2.4ms;
`GET /session` cold p95 ≈ 1.36s; `GET /session/:id/message` cold p50 ≈ 1.85s;
boot ≈ 2.8s, RSS ≈ 369MB. Hot paths are unaffected; cold reads are still the cost
of the upstream dsh full scan.

### 2026-08-16 late-night retest (v2 history endpoint, 1 session × 10k turns)

`node scripts/perf.mjs --sessions 1 --messages-per-session 10000 --quiet`:

| Metric | Value |
|---|---|
| `GET /api/session/:id/history?limit=100` cold read | ~1.4ms (including the first RPC) |
| `GET /api/session/:id/history?limit=100` hot p50/p95 | ~1.0 / 1.4ms |
| full pagination (20,000 messages, 100/page) | 200 pages / ~1.2s (about 6ms/page) |
| `GET /api/session/:id/message?limit=100` | ~2.1ms |

Conclusion: `after` uses dsh's native `beforeSeq` backward pagination (exclusive
upper bound), so each page's latency is bounded and no longer folds all events in
O(N); a full pass over 20k messages in a single session takes about 1.2s. The
generated session file is about 14.9 MiB (70k events).
